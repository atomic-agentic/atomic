# Design decisions

These are the choices the rest of atomic's design builds on. Each row gives the
choice, the reason for it, and what would make it worth reopening. The other
design pages work out what follows from each one.

## Decision log

| Decision | Why | Revisit if |
| --- | --- | --- |
| Durable execution comes from durare, forked to sqlx 0.9 and reached only through the `DurableRuntime` trait | It needs no separate cluster: it runs inside the atomic process on SQLite or Postgres, and the fork lets it share Codex's SQLite library | durare stops moving or drifts from DBOS-compatible behaviour; the trait is the way out, with a Postgres-only engine put behind it |
| Codex comes in as crates from a pinned fork, `atomic-agentic/codex`, which carries only small portability patches (today two `utils/pty` commits); Codex core is never modified | atomic gets Codex's sandbox, tools, model layer and client for free and follows upstream by moving one pin | The crates change faster than a scheduled bump can keep up with, or the fork starts to need patches beyond portability |
| A single binary acts as CLI, server and runner | There is one thing to install and upgrade, and a laptop needs no infrastructure | A runner image must shrink well below the size of the control plane |
| durare and the work graph live in the same database | The accepted result of a step and the graph writes it publishes commit together in one short transaction | At scale, graph writes need a database of their own |
| In v0.1 atoms run on Codex's `ThreadManager`; v0.5 moves them onto the app-server embedded in the process | A durable atom on the shortest known path first; the interactive client that requires app-server arrives in v0.5 | Never; this is only an ordering |
| Unattended deployments default to API keys, provider accounts or workload identity; using a personal account sign-in for automation must be configured on purpose | What an account is entitled to, and who a deployment acts as, differ from case to case; one person's subscription is not a credential for a service | A documented account path passes the deployment acceptance tests |
| In v0.1 an unfinished run is picked up again by `atomic runs resume <run-id>`, or by a local `atomic serve` | The first durable release needs a recovery command of its own that works without a TUI | Never; recovery is part of the v0.1 gate |
| Workflows start as declarative files; TypeScript and Rust workflows come later | Diffs stay readable and files are checked at load; code is kept for logic | Most people end up writing workflows as code |
| Convention over configuration: atomic detects defaults, explicit settings always win, and each default can be explained | A project can start with no configuration, without behaviour nobody can account for | Detection keeps surprising people in ways `atomic config --explain` cannot clear up |
| A declarative atom is an `.atom.astro` file: the bundled Astro parser reads it and a bounded TypeScript-shaped interpreter evaluates it, and it is never run as a module; helpers run one call at a time in an isolate with no capabilities | Authors keep Astro's syntax and editor support, yet a declarative file still cannot execute arbitrary code (see [atom files](../reference/atom-files.md)) | The supported subset turns out too narrow for real prompts, or its bounds cost too much |
| Code carried by an atom runs on Deno, with permissions derived from what the atom declares | Deno can allow network access per host, pins imported packages in a lockfile without an install step or install scripts, and brings its own transpiler and type checker | A second binary costs too much to ship, an SDK someone needs will not run on Deno, or Deno's Node compatibility gets worse; the fallbacks are linking Deno's crates or running a plain command in a pinned image |
| Atom code says whether it reads or writes, and evals, renders and previews never run code that writes | atomic cannot see what a script sends; only the declaration lets it retry reads freely and keep writes out of every dry run | People routinely label writes as reads to get them into evals |
| Cloud access uses named credentials that are issued per step and expire quickly | No long-lived key exists to store or leak, and the provider's own audit log records which run and step acted | A provider that matters offers nothing like a role-based credential |
| A behavioural test is ported before the code it describes, and confirmed against the implementation it came from | The ported tests become the specification, and the new code is written to pass them | A component turns out quicker to port than to rewrite |
| Moving agents from other frameworks is a gated, step-by-step workflow that atomic's own skill plans, on top of a mechanical importer | Most existing agents have to be rebuilt rather than kept, and each converted piece needs a review and a check against how the original behaved | Teams only ever use the importer, or the plans the skill files need more editing than writing them by hand |
| Time feeds readiness: graph items can carry `due_at` and workflows can wait durably, both through the trigger scheduler and the run inbox | Agents need follow-ups that say "not before"; a single scheduler keeps one active worker per run and recovers correctly after downtime | Due items and waits are so rare that gate deadlines and cron schedules cover them, or the scheduler polls too coarsely |
| Goals live in the graph as pinned items that keep a measure, a feedback log and an ignore list; questions to people are gates with typed answers that may be remembered; every wake begins with a `consider` step that may choose to do nothing | It reuses pinned items, child edges, gates, triggers and memories, and atoms stay shaped like tasks, so their tools and effects can still be declared (see [goals](planning.md#goals)) | A goal's history outgrows a graph item, or deciding whether to act costs too much on the cheapest tier |
| In the team and gateway profiles, agentgateway enforces policy on model and tool traffic at the wire, using configuration compiled from atomic's declarations; each request's JWT carries claims naming its run, project, atom, tenant and sensitivity label | Fallback, quotas, cost attribution and clearance are declared once rather than in two policy systems; the local profile keeps enforcement in process (see [enforcement point](model-layer.md#enforcement-point)) | The gateway cannot express something atomic needs to declare, or the generated configuration proves less robust than the in-process path |
| Keycloak is the reference identity provider; atomic only consumes identity, never implements SCIM, brokering or token exchange itself, and accepts any OIDC provider | Server, console, gateway and runner identities share one root of trust, and the issuer supplies provisioning, organizations, brokered tokens, delegation and step-up (see [identity and access](security.md#identity-and-access)) | Delegation or resource indicators remain in preview with fragile workarounds, or operators will not run another stateful service; then delegation is built against plain OIDC |
| A pack is an ordinary package that also knows how to install itself: one `packages:` key, one lock, one trust rule | A separate plugin mechanism would be another supply chain to secure; a pack's conditions can discover things but never grant anything (see [packs](developer-experience.md#packs)) | Packs need hooks into the runtime that definitions cannot express |
| A recorded decision names the evidence it rests on, and a separate command that takes a date, `atomic stale`, checks it | the evidence (eval results, benchmarks, past runs) is already in atomic's hands, so the conditions can be evaluated rather than merely stored; keeping the clock out of `atomic check` keeps checks reproducible | Teams record decisions but never act when they go stale |
